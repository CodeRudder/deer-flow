# 任务方案评审工作流

日期：2026-11-03
适用：所有派发给子代理的开发/修复任务

## 流程

1. **派发时分级**：
   - 排查/修复类 → 任务书写明"**先输出结论+方案，批准后才实施**"
   - 开发类 → 任务书写明"不确定的决策点列选项提交，不得自行拍板"；规格明确的常规实现可直接做
2. **方案提交**：子代理在动手（或深度实施）前提交方案：根因/契约/改动点/待决策选项/已做改动清单
3. **主会话评审**：对**重要任务方案**进行评审——对照用户需求与既有架构，做出决策：
   - 方案合格 → 批准实施
   - 有更优解 → 优化方案后下发
   - 有风险/越界 → 纠偏或退回
4. **实施与验收**：批准后实施；完成时按任务书验收（测试+实测证据），再收割汇报

## 决策记录（示例沉淀）

- 目录侧栏：虚拟根 /mnt/user-data、search 限 path 内递归、非图片走下载、第三栏+移动抽屉、默认收起——已批
- 视频结果不显示：根因=skill 交付契约缺口（未落盘 outputs+未 present_files）；方案=改 SKILL.md 交付契约+契约守护测试——待用户批
- 网关外部地址：env 双字段（EXTERNAL_BASE_URL/EXTERNAL_CONSOLE_URL）+ 优先级链，未配置兜底内部地址——待用户批

## 原则

- 用户决策优先；主会话只在规格已明确时代批，重要取舍必须呈现给用户
- 方案评审的目标是"决策优化方案还是开始开发处理"，不是流程拖慢——规格明确的常规部分允许直接实施
