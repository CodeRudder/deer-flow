# DeerFlow dev → prod 增量迁移操作手册

> 本手册只适用于本次一次性迁移。
>
> 数据窗口：北京时间 `[2026-07-13 00:00:00, 2026-07-20 00:00:00)`，即包含整个 7 月 19 日。
>
> 正式操作对象必须是真实 dev/prod PostgreSQL 和各自的 `DEER_FLOW_HOME`，不能使用本地开发环境代替。

## 1. 迁移原则

- 方向：`dev-deerflow` → `prod`。
- prod 从生成 target baseline 开始，到迁移标记为 `VERIFIED` 之前，必须始终停写。
- dev 在最终扫描和 export 期间必须停写。
- 同主键、同文件路径冲突时以 dev 为准。
- prod 独有数据保留，不同步 dev 删除。
- 迁移包中的运行控制文件只归档，不在 prod 激活。
- 所有命令从 DeerFlow 仓库的 `backend/` 目录执行。
- `--confirm-services-stopped` 只是人工确认参数，脚本不会替你停止服务。

## 2. 操作前准备

### 2.1 确认真实路径

在 prod 和 dev 分别确认：

- 仓库目录，例如 `/opt/deer-flow`。
- 配置文件，例如 `/opt/deer-flow/config.yaml`。
- `DEER_FLOW_HOME`，例如 `/data/deer-flow`。
- PostgreSQL 配置确实指向当前环境。

下面使用这些示例变量，执行前必须替换成真实路径。

prod：

```bash
export PROD_REPO=/opt/deer-flow
export PROD_CONFIG=/opt/deer-flow/config.yaml
export PROD_HOME=/data/deer-flow
export MIGRATION_ROOT=/secure/deerflow-migration
export MIGRATION_ID=$(uuidgen | tr '[:upper:]' '[:lower:]')
export STATE_DIR="$MIGRATION_ROOT/$MIGRATION_ID"
export PROD_BASELINE="$STATE_DIR/baseline.json"
export PROD_PACKAGE="$STATE_DIR/deerflow-incremental.tar.gz"

# 只创建父目录，不要提前创建或填充 STATE_DIR
install -d -m 700 "$MIGRATION_ROOT"
```

dev：

```bash
export DEV_REPO=/opt/deer-flow
export DEV_CONFIG=/opt/deer-flow/config.yaml
export DEV_HOME=/data/deer-flow
export DEV_MIGRATION_ROOT=/secure/deerflow-migration
export MIGRATION_ID=<填写-prod-生成的同一个-MIGRATION_ID>
export DEV_BASELINE="$DEV_MIGRATION_ROOT/$MIGRATION_ID/baseline.json"
export DEV_PACKAGE="$DEV_MIGRATION_ROOT/$MIGRATION_ID/deerflow-incremental.tar.gz"
export DEV_WORK_ROOT="$DEV_MIGRATION_ROOT/work"

install -d -m 700 "$(dirname "$DEV_BASELINE")" "$DEV_WORK_ROOT"
```

固定时间参数：

```bash
export MIGRATION_START='2026-07-13T00:00:00+08:00'
export MIGRATION_END='2026-07-20T00:00:00+08:00'
```

### 2.2 前置检查

执行正式迁移前必须完成：

1. 对 prod PostgreSQL 做一次独立备份，例如 `pg_dump`。
2. 对 prod `DEER_FLOW_HOME` 做文件快照或备份。
3. 确认 prod state 盘、prod 文件盘、PostgreSQL tablespace/WAL 空间足够。
4. 确认 dev/prod PostgreSQL 主版本和 public schema 一致。
5. 确认迁移账号可以读取全部 public 表和 `pg_catalog`；prod 账号还需要建删 schema、锁表、DML 和调整 sequence 的权限。
6. 如果存在 legacy 路径 `${DEER_FLOW_HOME}/threads/<thread_id>` 且数据库无法确定 owner，准备 owner map：

```json
{
  "thread-id-1": "user-id-1",
  "thread-id-2": "user-id-2"
}
```

保存为安全路径，例如 `/secure/deerflow-migration/owner-map.json`。如果不需要 owner map，后续命令不要带 `--owner-map`。

7. 如果迁移包含 `channel_credentials`，确认 dev/prod 的渠道凭据加密密钥兼容；未确认前不能执行正式 import。
8. dev 和 prod 使用包含本迁移工具的同一代码版本，并记录版本：

```bash
cd /opt/deer-flow
git rev-parse HEAD
cd backend
uv run python -m scripts.migrate_incremental_data --help >/dev/null
```

## 3. 第一步：停止 prod 写入

按 prod 实际部署方式停止所有写入者，包括：

- Gateway/API。
- Agent worker 和后台任务。
- IM/channel 服务。
- 其他会写 DeerFlow PostgreSQL 或 `DEER_FLOW_HOME` 的进程。

常见部署方式选择对应命令，不要全部执行：

```bash
# 本地进程部署
cd "$PROD_REPO" && make stop

# Docker 生产部署
cd "$PROD_REPO" && make down

# Docker 开发式部署
cd "$PROD_REPO" && make docker-stop
```

停止后检查进程/容器，并在数据库中确认没有 `pending` 或 `running` 的 run。迁移脚本也会再次检查；只要仍有活动 run 就会阻断。

从此刻起，prod 必须保持停写，直到第 11 步标记 `VERIFIED`。

## 4. 第二步：在 prod 冻结 baseline

### 4.1 可选：只读预览

不带 `--apply` 只做扫描，不创建 state/baseline：

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data plan target \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR" \
  --migration-id "$MIGRATION_ID" \
  --start "$MIGRATION_START" \
  --end "$MIGRATION_END" \
  --source-environment dev-deerflow \
  --environment prod
```

检查输出中的 `table_count`、`row_count`、`file_count` 和 `runtime_control_count` 是否合理。

### 4.2 正式冻结

`STATE_DIR` 必须位于 `PROD_HOME` 之外，并且必须为空。不要提前在里面放 baseline 或迁移包。

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data plan target \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR" \
  --baseline-output "$PROD_BASELINE" \
  --migration-id "$MIGRATION_ID" \
  --start "$MIGRATION_START" \
  --end "$MIGRATION_END" \
  --source-environment dev-deerflow \
  --environment prod \
  --apply \
  --confirm-services-stopped
```

成功输出必须满足：

- `applied` 为 `true`。
- `migration_id` 等于 `$MIGRATION_ID`。
- `baseline_path` 指向生成的 baseline。
- `$STATE_DIR/state.json` 中 phase 为 `BASELINE_FROZEN`。

检查：

```bash
jq '{export_id, phase, details}' "$STATE_DIR/state.json"
ls -la "$STATE_DIR"
```

此步骤会把 prod 已有运行控制文件放入 state 下的可回滚 quarantine。不要手工移动或删除 state 内任何文件。

如果此步骤在创建 state 后失败，不要使用同一个 state 目录重新执行 `plan target`；保持 prod 停写并执行第 13 节 rollback，或者使用全新的 migration ID/state 从头开始。

## 5. 第三步：把 baseline 安全传到 dev

只把 baseline 文件传到 dev，prod 的整个 state 目录必须继续保留在 prod。

示例：

```bash
# 在 prod 执行；远端目录按实际修改
ssh dev-host "install -d -m 700 /secure/deerflow-migration/$MIGRATION_ID"
scp "$PROD_BASELINE" \
  "dev-host:/secure/deerflow-migration/$MIGRATION_ID/baseline.json"
```

传输后在两端比较 SHA-256：

```bash
sha256sum "$PROD_BASELINE"   # prod
sha256sum "$DEV_BASELINE"    # dev
```

macOS 可用 `shasum -a 256` 代替 `sha256sum`。

两个值必须完全一致。迁移文件含业务数据，必须使用受控、加密的传输通道。

## 6. 第四步：停止 dev 写入

按 dev 实际部署方式停止 Gateway、worker、IM/channel 和其他写入者。例如：

```bash
cd "$DEV_REPO" && make stop
```

停止后确认 dev 数据库没有 `pending`/`running` run，也没有进程继续修改 `$DEV_HOME`。

dev 必须从最终 source plan 开始保持停写，直到 export 完成并校验成功。

## 7. 第五步：在 dev 生成 source plan

```bash
cd "$DEV_REPO/backend"

uv run python -m scripts.migrate_incremental_data plan source \
  --config "$DEV_CONFIG" \
  --home "$DEV_HOME" \
  --baseline "$DEV_BASELINE" \
  --start "$MIGRATION_START" \
  --end "$MIGRATION_END"
```

如果需要 owner map，在命令末尾增加：

```bash
  --owner-map /secure/deerflow-migration/owner-map.json
```

检查输出：

- `selected_thread_count`：本次选中的 thread 数量。
- `selected_thread_digest`：选集摘要，保存到操作记录中。
- `activity_thread_count`：时间窗口活动 thread 数量。
- `changed_database_thread_count`：数据库 key/hash 差异发现的 thread 数量。
- `changed_file_thread_count`：文件差异发现的 thread 数量。
- `selected_file_count`、`selected_file_bytes`：文件规模。
- `table_rows`：各表扫描/导出规模。

以下任一情况都不能继续：

- source/target schema fingerprint 不一致。
- PostgreSQL 主版本不一致。
- 出现未分类或不支持的 public 表。
- bookkeeping 版本数据不一致。
- thread 缺少 owner 或 owner 冲突。
- 仍有活动 run。

## 8. 第六步：在 dev 生成迁移包

输出文件必须不存在；如果之前生成过包，使用新路径，不要覆盖。

```bash
cd "$DEV_REPO/backend"

uv run python -m scripts.migrate_incremental_data export \
  --config "$DEV_CONFIG" \
  --home "$DEV_HOME" \
  --baseline "$DEV_BASELINE" \
  --start "$MIGRATION_START" \
  --end "$MIGRATION_END" \
  --source-environment dev-deerflow \
  --target-environment prod \
  --output "$DEV_PACKAGE" \
  --work-root "$DEV_WORK_ROOT" \
  --apply \
  --confirm-services-stopped
```

如果需要 owner map，增加与第 7 步相同的 `--owner-map`。

检查成功输出：

- `export_id` 等于 prod baseline 的 migration ID。
- `package_path` 等于 `$DEV_PACKAGE`。
- `selected_thread_count` 与第 7 步一致。
- `table_count`、`database_row_count`、`file_count`、`file_bytes` 合理。

记录包的外层 SHA-256：

```bash
sha256sum "$DEV_PACKAGE" | awk '{print $1}' | tee "$DEV_PACKAGE.sha256"
ls -lh "$DEV_PACKAGE"
```

迁移包是单个 `tar.gz`，其中数据库数据是 PostgreSQL text COPY 的 gzip 流，不是 CSV，也不是 `pg_dump`。

export 成功后 dev 是否恢复服务由上线安排决定；prod 仍然必须保持停写。

## 9. 第七步：把迁移包安全传回 prod

示例：

```bash
# 在 dev 执行；目标地址按实际修改
scp "$DEV_PACKAGE" \
  "prod-host:/secure/deerflow-migration/$MIGRATION_ID/deerflow-incremental.tar.gz"
scp "$DEV_PACKAGE.sha256" \
  "prod-host:/secure/deerflow-migration/$MIGRATION_ID/deerflow-incremental.tar.gz.sha256"
```

在 prod 校验外层 SHA-256：

```bash
test "$(sha256sum "$PROD_PACKAGE" | awk '{print $1}')" = "$(cat "$PROD_PACKAGE.sha256")" \
  && echo 'package sha256 OK'
```

两边必须一致。脚本还会校验包内 `checksums.sha256`、manifest、baseline、数据库 payload 和文件 archive。

## 10. 第八步：在 prod 执行 dry-run

prod 继续保持停写。

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data import \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR" \
  --package "$PROD_PACKAGE"
```

如果使用 owner map，必须传入同一份映射：

```bash
  --owner-map /secure/deerflow-migration/owner-map.json
```

成功输出必须满足：

- `applied` 为 `false`。
- phase 通常为 `BASELINE_FROZEN`。
- `database.conflicts` 为空。
- 每张表的 `insert_count`、`update_count`、`same_count`、`target_only_count` 数量合理。
- 文件 `created`、`replaced`、`unchanged`、`runtime_archived` 数量合理。
- `$STATE_DIR/import-report.json` 已生成。

`target_only_count` 不一定必须为 0；它表示 prod baseline 中存在而 dev 包未覆盖的记录，本需求默认保留。但任何 hard conflict 都必须先停止调查，不能绕过。

重点查看：

```bash
jq . "$STATE_DIR/import-report.json"
```

不能继续的冲突包括 owner、主键逻辑、业务唯一键、run event logical key、checkpoint parent/write、schema 或 baseline 后 prod 分叉。

dry-run 不会修改业务表和 active 文件，也不会持久保留临时 staging schema。

## 11. 第九步：在 prod 正式 import

只有 dry-run 无 hard conflict，且确认 prod 仍然完全停写后才能执行。

如果输出中 `credential_key_confirmation_required=true`，必须先验证 dev/prod 渠道凭据加密密钥兼容，再带 `--confirm-credential-key-compatible`。如果不包含渠道凭据，该参数可以不传。

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data import \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR" \
  --package "$PROD_PACKAGE" \
  --apply \
  --confirm-services-stopped \
  --confirm-credential-key-compatible
```

如果使用 owner map，继续传同一个 `--owner-map`。

正式 import 会依次执行：

1. 校验目标 PostgreSQL cluster/database、`PROD_HOME`、批准时间窗口和环境标签。
2. 校验并绑定逻辑包摘要 `package_content_sha256`。
3. 在 prod PostgreSQL 创建工具 staging schema。
4. 加载 COPY payload 并执行冲突预检。
5. 在数据库事务中保存 backup、合并 source-wins 数据并调整 sequence。
6. 按文件 journal 保存备份并合并 active 文件。
7. 将源端运行控制文件保留在 archive，不激活。
8. 执行离线 overlay 校验。

成功后 state 通常是 `VERIFYING`，不是 `VERIFIED`：

```bash
jq '{phase, details}' "$STATE_DIR/state.json"
```

此时仍然不能启动 prod。

必须保留：

- `$STATE_DIR/state.json`
- `$STATE_DIR/frozen-baseline.json`
- `$STATE_DIR/package/`
- `$STATE_DIR/target-file-backup/`
- `$STATE_DIR/target-runtime-quarantine/`
- 两个 file journal
- prod PostgreSQL 中的 `deerflow_migration_<migration-id>` staging schema

## 12. 第十步：执行离线 verify

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data verify \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR"
```

如果使用 owner map，继续传同一个 `--owner-map`。

检查输出：

- `verified` 此时为 `false`，表示只读数据校验通过，但还未完成人工验收。
- `table_count`、`row_count` 合理。
- `active_file_count`、`runtime_archive_file_count` 与 import 报告一致。
- 命令无 schema、marker、数据库 overlay 或文件 overlay 错误。

## 13. 第十一步：人工 smoke test 并标记 VERIFIED

工具不会自动执行 API smoke test。prod 仍保持停写，在只读维护实例或隔离实例中至少验证：

1. 管理员/普通用户可读取。
2. 迁移用户和旧 thread 可见。
3. 旧消息、run/event 可读取。
4. checkpoint 可以恢复读取，parent/write 不断裂。
5. 上传、workspace、outputs、子 agent 文件可读取。
6. legacy thread 路径内容可读取。
7. channel credentials 如参与迁移，可以正常解密/加载。
8. 运行控制文件没有被直接重新激活。

人工验收通过后才标记终态：

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data verify \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR" \
  --apply \
  --confirm-services-stopped \
  --confirm-smoke-tests
```

成功输出必须为：

- `verified: true`
- `$STATE_DIR/state.json` 中 `phase: VERIFIED`

检查：

```bash
jq '{export_id, phase, details}' "$STATE_DIR/state.json"
```

`VERIFIED` 是终态。进入该状态后不要再执行 import 或内置 rollback。

## 14. 第十二步：恢复 prod 服务

只有 state 明确为 `VERIFIED` 后才能恢复 prod：

```bash
jq -e '.phase == "VERIFIED"' "$STATE_DIR/state.json"
```

然后按实际部署方式启动。例如：

```bash
# 本地生产模式
cd "$PROD_REPO" && make start

# Docker 生产部署
cd "$PROD_REPO" && make up

# Docker 开发式部署
cd "$PROD_REPO" && make docker-start
```

恢复后持续观察：

- Gateway/worker/channel 日志。
- PostgreSQL 错误、唯一键冲突和连接异常。
- 用户、thread、checkpoint、文件读取。
- 渠道凭据解密异常。

不要立即删除 state、迁移包、数据库 staging schema、文件备份和迁移前灾备。按运维审计保留期统一清理。

## 15. 失败和回滚

### 15.1 任何失败时的第一原则

1. prod 保持停写，绝不能直接启动服务。
2. 不要删除 state、package、staging schema、journal 或 backup。
3. 查看 state：

```bash
jq . "$STATE_DIR/state.json"
```

4. 如果命令被 `Ctrl-C` 中断，不能假设未产生修改。CLI 不会对 `Ctrl-C` 自动 rollback。
5. 命令 exit code 为 `2` 也不能直接判断迁移停在哪一步；正式 import 失败后可能已经自动补偿到 `ROLLED_BACK`，必须以 `state.json` 和 PostgreSQL staging marker 为准。
6. 如果 baseline 后 prod 曾被误启动并产生新写入，不要直接执行内置 rollback。先重新停写、做额外快照并人工对账，否则 rollback 可能删除或覆盖这些新写入。

### 15.2 状态处理表

| phase | 处理方式 |
| --- | --- |
| `TARGET_PREFLIGHT` | target baseline 尚未完成。保持停写，优先执行 rollback；不要在同一 state 重跑 `plan target`。 |
| `BASELINE_FROZEN` | 可以修正包/传输问题后重新 dry-run 或用同一包 apply；放弃时 rollback。 |
| `STAGED` | 可用同一包重新执行 import apply；遇到业务冲突不要绕过，放弃时 rollback。 |
| `DB_APPLYING` | 事务可能提交也可能未提交；使用同一 prod 配置、同一 state、同一包重新执行 import apply，让 marker 恢复状态。 |
| `DB_COMMITTED` | 数据库已提交、文件未完成；用同一包重跑 import apply，或 rollback。 |
| `FILES_APPLYING` | 文件可能部分安装；保持停写，优先执行显式 rollback，不要删除 journal。 |
| `FILES_APPLIED` / `VERIFYING` | 可重跑 verify；如果验收失败或决定放弃，执行 rollback。 |
| `ROLLBACK_IN_PROGRESS` | 回滚曾中断，重复同一 rollback 命令继续。 |
| `ROLLBACK_FAILED` | 绝不能启服务；修复连接、权限、磁盘或文件问题后重复 rollback，直到 `ROLLED_BACK`。 |
| `ROLLED_BACK` | 已恢复 baseline，可恢复原 prod；如需重试迁移，必须使用新的 migration ID/state/baseline/package。 |
| `VERIFIED` | 迁移终态，不能使用内置 rollback；需要恢复时必须走独立灾备和人工恢复流程。 |

极少数情况下，如果 `verify --apply` 在数据库 marker 已变为 `verified`、但 `state.json` 仍是 `VERIFYING` 时中断，保持 prod 停写，不要盲目 import 或 rollback；保留现场并人工核对 PostgreSQL staging marker 与 state 后再处理。

### 15.3 rollback 预览

不带 `--apply` 只显示当前 phase，不会真正回滚：

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data rollback \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR"
```

### 15.4 正式 rollback

```bash
cd "$PROD_REPO/backend"

uv run python -m scripts.migrate_incremental_data rollback \
  --config "$PROD_CONFIG" \
  --home "$PROD_HOME" \
  --state-dir "$STATE_DIR" \
  --apply \
  --confirm-services-stopped
```

如果使用 owner map，继续传同一个 `--owner-map`。

成功后必须满足：

```bash
jq -e '.phase == "ROLLED_BACK"' "$STATE_DIR/state.json"
```

rollback 会尝试：

- 删除本次数据库 insert。
- 恢复被覆盖的数据库行。
- 恢复 sequence 原值。
- 恢复被替换/创建的文件。
- 恢复 prod baseline 前隔离的运行控制文件。
- 删除本次 PostgreSQL staging schema。
- 对账确认目标回到 frozen baseline。

只有成功进入 `ROLLED_BACK` 后，才可以恢复原 prod 服务。如果仍是 `ROLLBACK_FAILED`，继续保持停写。
