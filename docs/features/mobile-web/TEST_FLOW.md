# DeerFlow 移动端 — 测试流程清单

> 配套：`DEVELOPMENT_PLAN.md`（设计与任务）、`FEATURE_LIST.md`（功能范围）
> 目的：先列清「要测什么、每步期望什么、由哪一层证明」，再据此写 E2E 用例。

## 0. 三层测试，各自能证明什么

选错层会写出「看起来在测、其实测不到」的用例，所以先划清边界。

| 层 | 命令 | 能证明 | **证明不了** |
|---|---|---|---|
| **单测** | `pnpm test`（Rstest） | 纯函数、组件渲染、i18n | 任何需要真实路由/中间件的事 |
| **E2E（mock 后端）** | `pnpm test:e2e` | 真 Next 服务上的路由分流、页面渲染、交互、请求载荷 | **登录流程本身**（见下） |
| **真机栈** | `make dev` → `localhost:2026` | 端到端真实链路：真实网关、真实鉴权、真实模型 | 不适合当开发内环（慢） |

**E2E 测不到登录流程，这是结构性的**：`playwright.config.ts` 用
`DEER_FLOW_AUTH_DISABLED=1` 启动，`getServerSideUser()` 见到该标志会**在任何
HTTP 请求之前**返回一个合成的已登录用户。于是：

- 登录页在 E2E 里**永远渲染不出来**（守卫先于渲染把它重定向掉了）
- `page.route()` 也拦不到 —— 根本没有请求发出

因此登录页本身的断言放在 `tests/unit/app/m/mobile-auth-pages.test.tsx`
（渲染），中间件分流放在 `tests/e2e/mobile-auth.spec.ts`（读
`x-middleware-rewrite` 响应头），**完整链路只能在真机栈上人工走一遍**。

### G10 详解：相册/拍照丢文件（已由 T15 修复，保留作参考）

`src/components/workspace/mobile/composer.tsx:176-183`：

```js
const { files } = event.target;   // 取到 FileList 对象本身，不是快照
event.target.value = "";          // 按 HTML 规范：同一个对象被清空
if (!files || files.length === 0) return;   // 恒为 0，直接 return
```

`input.files` 返回的是**同一个 `FileList` 对象**（直到选择发生变化，而
`value = ""` 正是这种变化），所以先取引用、再重置 value，拿到的是「已经被清空的
那个对象」。实测（同一 Chromium，`setInputFiles` 后走一遍该 handler 序列）：

```
before=1  names=["probe.png"]  after=0  sameAcrossAccess=true
相册 chips: 0    拍照 chips: 0    文件 chips: 1
```

文件入口正常，是因为它走 `ai-elements` 的隐藏 input；
`prompt-input.tsx:718-726` 先用 `Array.from` 快照、再重置 `value`。修法即「先快照
后重置」，一行的事。

### G7 详解：发送失败丢输入（根因已修正）

> **勘误**：本节初稿把根因写成「`handleSubmit` 无附件路径返回 `undefined`，
> 被 `prompt-input.tsx` 当成同步成功」。**这是错的**，T11 实测推翻了它：
> 照着改完，bug 依旧 100% 复现。以下是插桩后的真实结论。

`langgraph-sdk` 的 `StreamManager.start` 是 **fire-and-forget**：

```js
// node_modules/@langchain/langgraph-sdk/dist/ui/manager.js:291
start = async (action, options) => {
  this.queueSize += 1;
  this.queue = this.queue.then(() => this.enqueue(...));   // 只入队
};
```

`submit` await 的是这个**入队**动作，所以 `sendMessage` 在 `/runs/stream`
请求**发出之前**就已经 resolve —— **有附件时也一样**。于是：

- 失败的 run 永远无法 reject 那个 promise；
- `prompt-input.tsx` 自己的错误分支（`// Don't clear on error`）对 **run 失败
  根本不可达**；
- 原判断「promise vs void 两条路径不一致」只对**上传失败**成立，与本次现象无关。

实测时间线（`/runs/stream` mock 成 500）：

```
handleSubmit 返回 promise = true
promise 在 t+0 就 RESOLVED
/stream 请求在 promise 之后 41ms 才发出     ← 关键
t+77ms   输入框空（clearSubmittedState）
t+23.2s  错误 toast 出现
```

**已修**（`use-chat-page.ts`）：暂存已提交文本，等 `thread.error` 出现时写回，
且**绝不覆盖**用户之后新输入的内容。同时让 `handleSubmit` 两条路径都返回 promise，
以修复上传失败路径的不一致。

**遗留不足（诚实记录）**：输入框仍在 77ms 时被清空，**23 秒后**才把文字还回来 ——
是「消失一下再回来」，不是「从头到尾不丢」。要真正做到不丢，只能改
`prompt-input.tsx`（`ai-elements/**` 是注册表生成物，禁止手改），或者把清空
推迟到「run 确认已开始」—— 但没有 per-run 的 started 信号（`onStart` 每个 thread
只触发一次），推迟会导致第 2 条消息起输入框永不清空，那个回归更糟。

### 流式测试的技术前提（G8）

**不能用「挂住 `page.route()`」来伪造流进行中**：AbortController 会触发、
`net::ERR_ABORTED` 也能观察到，但 rejection 传不到 SDK，输入区会永远停在
「停止生成」—— 得到的是假失败。已实测确认。

正确做法二选一：

1. **spec 内起一个回环 SSE 服务**（`http.createServer`），用
   `page.route(..., r => r.continue({ url }))` 把 `/runs/stream` 指过去。
   优点：完全控制每个 chunk 的时序，确定性断言「中途」状态，不依赖真实模型。
2. **走真机栈**（`pnpm test:live`）：真实模型真实 SSE，最可信，但节奏不可控、
   有 token 成本，只适合断言「最终结果 + 期间出现过停止按钮」。
| G2 | 登录/SSO 全链路只有人工 | 改动 auth 时无回归网 | 需要一个带真实网关的 E2E 档位，或接受人工 |
| G3 | 会话过期无处理（E5） | 用户可能卡在空白页 | 属 N5，未实现 |
| G4 | 停止 / 重试 / 分页加载无移动端用例 | 流式中断类回归测不到 | 补 E2E |
