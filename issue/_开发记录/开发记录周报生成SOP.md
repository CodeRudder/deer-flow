# 开发记录周报生成 SOP

本文档用于规范“按分支、时间范围统计项目开发记录，并生成半月维度 Markdown 汇报材料”的固定流程。后续执行时，应先按照本 SOP 搜集和归并信息，再生成最终的双周变更 MD 文档。

## 1. 目标

从 Git 提交记录中提炼一份适合群内同步、工作汇报、阶段复盘使用的开发记录。最终结果不是 commit 流水账，而是按工作周整理后的功能变更说明。

## 2. 输入信息

执行前需要明确以下信息：

- 目标仓库：当前项目仓库。
- 目标分支：例如 `develop`。
- 提交人范围：默认统计所有提交人；只有用户明确要求时，才按指定开发人过滤，例如 `zhangxin`。
- 统计范围：起始 commit / 起始日期 到 截止 commit / 截止日期。
- 输出目录：默认放在 `issue/_开发记录/`。
- 输出格式：Markdown。

默认示例：

```bash
git log --date=short --pretty=format:'%h%x09%ad%x09%s' <start>..<end>
```

如果需要包含起始 commit 本身，使用：

```bash
git log --date=short --pretty=format:'%h%x09%ad%x09%s' <start>^..<end>
```

如果用户明确要求按开发人过滤，再增加 `--author`：

```bash
git log --author='zhangxin' --date=short --pretty=format:'%h%x09%ad%x09%s' <start>..<end>
```

## 3. 输出文档结构

最终汇总文档按半月生成，每个文档包含连续两个工作周。正文和汇总栏均按日期倒序排列，最近一周放在最前面。

```md
# DeerFlow 开发记录汇总

统计范围：YYYYMMDD-YYYYMMDD
分支：develop
统计提交人：所有提交人

## 汇总

| 序号 | 周期 | 核心模块 | 重点概括 |
| --- | --- | --- | --- |
| 01 | YYYYMMDD-YYYYMMDD | 模块 A / 模块 B | 用一句话概括最近一周围绕这些模块形成的阶段成果。 |
| 02 | YYYYMMDD-YYYYMMDD | 模块 C / 模块 D | 用一句话概括前一周围绕这些模块形成的阶段成果。 |

## 01｜YYYYMMDD-YYYYMMDD

### 本周重点
- 模块 A：...
- 模块 B：...

### 新功能
- ...

### bug 修复
- ...

### 功能改造
- ...

### chore
- ...

### 官方分支合并
- ...

## 02｜YYYYMMDD-YYYYMMDD

### 本周重点
- 模块 C：...
- 模块 D：...
```

没有内容的分类可以省略，不需要保留空标题。

### 3.1 半月统计周期

- 默认一个文档统计连续两个完整工作周，以半月作为一个汇报周期。
- 工作周按周一至周五划分，例如 `20260817-20260821`、`20260824-20260828`。
- 周六日不单独作为一个周期；统计范围包含周末或边界零散日期时，先归整为选定的两个完整工作周，超出的零散日期不纳入本半月文档，不额外生成第三段。
- 一个半月文档的汇总栏和正文原则上各对应两周，序号和顺序保持一致。
- 本 SOP 中“半月”指连续两个工作周，不按自然月的 1-15 日或 16 日至月底切割。

例如：`20260814-20260828` 如果按两个完整工作周统计，应归整为 `20260817-20260828`，正文只保留 `20260817-20260821` 和 `20260824-20260828` 两段。

### 3.2 顶部汇总栏

半月汇总文档必须在正文前增加 `汇总` 区域，让读者先看到两周的主要更新，再跳转到下方详情。

推荐使用 Markdown 表格，并用编号对应下方详情。不要默认使用 `#标题锚点` 跳转，因为部分公司内部文档平台导入 Markdown 后，会把锚点误识别为文件引用，导致提示“文件已被移除”。

```md
## 汇总

| 序号 | 周期 | 核心模块 | 重点概括 |
| --- | --- | --- | --- |
| 01 | 20260630-20260703 | 视觉模型体系 / PostgreSQL 配置 | 完善独立视觉模型配置和 PostgreSQL 依赖基础，补齐模型能力与持久化能力落地条件。 |

## 01｜20260630-20260703
```

要求：

- 汇总栏用序号对应下方周详情，优先保证导入内部文档平台后的兼容性。
- 汇总栏中的 `核心模块` 和 `重点概括` 来自各周 `本周重点`，不要另写一套口径。
- 汇总栏只放重点，不放 commit、文件名、内部实现细节。
- 如果明确知道目标平台支持标题锚点，且用户确认需要点击跳转，可以再改用平台兼容的原生链接。

### 3.3 日期格式

- 文档标题、统计范围、汇总表、周详情标题和文件名中的日期统一使用 `YYYYMMDD`。
- 日期区间统一写成 `YYYYMMDD-YYYYMMDD`，日期内部不使用横杠，区间连接符使用一个半角 `-`，前后不留空格。
- 不使用 `YYYY-MM-DD`、`YYYY-MM-DD ~ YYYY-MM-DD` 或 `YYYY-MM-DD 至 YYYY-MM-DD` 等其他形式。
- Git 命令输出的日期可以保留工具默认格式，但写入最终文档前必须转换为统一格式。

示例：

```text
单日：20260706
区间：20260706-20260718
```

### 3.4 展示顺序

- 半月汇总按两个工作周的日期倒序排列，最近一周放在最前。
- 单周文档不需要倒序处理。
- 顶部汇总栏和下方详情的周顺序必须保持一致。

### 3.5 图标、表情和图表确认

如果文档中准备加入图标、表情符号、图表、统计图或 Mermaid 图，需要先和用户确认样式后再落稿。

默认可选方案：

- 纯文本：兼容性最好，适合正式汇报。
- Emoji：可读性强，适合群同步和轻量周报。
- 符号前缀：例如 `[重点]`、`[新增]`、`[修复]`，适合文档平台不稳定渲染 emoji 的情况。
- 图表：只有在需要展示趋势、数量对比、模块占比时再使用，不为装饰而加图。

推荐 Emoji 映射需先确认：

```text
本周重点：📌
新功能：✨
bug 修复：🐛
功能改造：🔧
chore：🧹
官方分支合并：🔀
```

## 4. 分类规则

### 新功能

归入新增用户能力、系统能力、平台能力、接口能力、工具能力等。

常见 commit 类型：

- `feat`
- 新增脚本、页面、接口、配置能力
- 新增模型、工具、技能、存储能力

示例表达：

- 完善图像生成能力，支持 OpenAI / Qwen 等图像模型接入，扩展可用模型范围。
- 新增历史会话数据迁移脚本，支持将遗留会话数据迁移到管理员账户。

### bug 修复

归入已存在功能的异常修复、崩溃修复、数据丢失修复、兼容性问题修复等。

常见 commit 类型：

- `fix`
- `revert`，如果是为了回滚有问题的改动

示例表达：

- 修复历史对话加载过程中的闪退和渲染异常。
- 修复子任务执行时 session 写入阻塞导致记录丢失的问题。

### 功能改造

归入已有能力的重构、行为调整、交互优化、内部逻辑改造。它通常不是全新功能，也不是单纯修 bug。

常见 commit 类型：

- `refactor`
- `style`，如果是和业务功能展示相关的样式统一
- 已有组件、已有中间件、已有流程的结构调整

示例表达：

- 重构工件文件列表组件，使其支持消息变体场景。
- 优化主会话中间件的消息去重逻辑，降低重复消息对会话记录的影响。

### chore

归入维护性、工程化、配置、文档、依赖、性能和稳定性优化类工作。之前单独提到的“稳定性 / 性能优化”和“文档 / 配置 / 工程化”统一放入 `chore`。

常见 commit 类型：

- `chore`
- `docs`
- `perf`
- 依赖更新
- 配置调整
- 文档更新
- 测试、lint、脚本、包源、部署辅助项
- 非 bug 修复性质的稳定性优化

示例表达：

- 优化子任务状态轮询策略，减少前端无效请求和状态刷新压力。
- 更新记忆管理相关文档，补充配置和使用说明。
- 切换后端包索引源，改善依赖安装稳定性。

### 官方分支合并

只统计明确的官方分支合并记录，例如：

- `Merge remote-tracking branch 'upstream/main' ...`
- 合并官方 `main` / `master` / `develop` 分支

如果某一周没有官方分支合并，则省略该分类。

## 5. 信息搜集步骤

### 5.1 确认当前分支和工作区

```bash
git branch --show-current
git status --short
```

注意：如果工作区存在未提交改动，只读取信息，不要回滚或覆盖用户改动。

### 5.2 拉取提交列表

默认按时间范围或 commit 范围获取所有提交：

```bash
git log --reverse --date=short --pretty=format:'%h%x09%ad%x09%s' <start>^..<end>
```

建议使用 `--reverse`，方便按时间线理解功能演进。

只有用户明确要求按开发人过滤时，才增加 `--author`：

```bash
git log --reverse --author='zhangxin' --date=short --pretty=format:'%h%x09%ad%x09%s' <start>^..<end>
```

日期口径：

- 周归属以 Git 作者日期（`%ad`）为准，因为 `--date=short` 展示的就是作者日期。
- 历史提交可能经过 rebase 或迁移，导致作者日期（`%ad`）与提交落库日期（`%cd`）不同；遇到这种情况，以作者日期归档，并在统计说明中注明。
- 如果作者日期和提交落库日期不一致，不要直接把 `--since` / `--until` 的结果作为最终周统计；应先拉取候选提交，再按 `%ad` 筛选和划分工作周。

按作者日期直接输出统一格式并筛选时，可使用：

```bash
git log <refs> --date=format:%Y%m%d --pretty=format:'%H%x09%ad%x09%an%x09%s' |
  awk -F '\t' '$2 >= "YYYYMMDD" && $2 <= "YYYYMMDD"'
```

### 5.3 拉取提交涉及文件

用于辅助判断提交属于前端、后端、技能、配置还是脚本：

```bash
git log --reverse --date=short --name-status --pretty=format:'----%n%h%x09%ad%x09%s' <start>^..<end>
```

### 5.4 必要时查看单个提交详情

对难以归类或标题含糊的提交，查看摘要：

```bash
git show --stat --oneline <commit>
```

如果仍不清楚，可以查看局部 diff，但最终文档不应摘抄大量代码细节。

## 6. 工作周划分规则

- 半月文档默认包含两个连续的完整工作周。
- 工作周按周一到周五划分，周六日不单独列出周详情。
- 用户给出的统计范围如果跨越周末或包含边界零散日期，先归整为两组完整工作周；超出的边界日期不纳入本半月文档，不因边界日期额外拆出第三段。
- 每个提交按照作者日期归入对应周；作者日期与提交落库日期不一致时，以作者日期为准。
- 周标题使用 `YYYYMMDD-YYYYMMDD`。

示例：

```md
## 01｜20260824-20260828
## 02｜20260817-20260821
```

## 7. 合并同类项规则

生成汇报时不要逐条翻译 commit，需要先做同类合并。

### 7.1 连续提交合并

同一周内围绕同一功能的多次提交，应合并成一个或少数几个功能点。

示例：

- 图像生成支持选择提供商
- 添加模型描述
- 默认宽高比调整
- 添加 OpenAI 图像生成支持
- 支持多种图像生成模式

可以合并为：

- 完善图像生成能力，支持多提供商选择、模型描述、默认尺寸调整和 OpenAI 图像模型接入。

### 7.2 临时修复归入主功能

如果某个 bug 修复紧跟在新功能开发过程中，并且明显属于该功能的补充修正，可以并入该功能点，不必单独写成 bug 修复。

如果修复跨周、影响面独立，或修复的是线上/已有能力，则应作为 bug 修复单独列出。

### 7.3 避免过细描述

不要把内部文件名、函数名、测试名作为汇报主体，除非它们是对技术团队有价值的关键上下文。

不推荐：

- 修改 `message-list.tsx`，调整 `artifact-file-list.tsx` 参数。

推荐：

- 优化消息列表中的工件展示逻辑，支持更复杂的消息变体场景。

### 7.4 表达收益

每条尽量体现收益或影响。

不推荐：

- 添加 JWT。

推荐：

- 增加公司网关 JWT 身份验证支持，为线上接入和租户隔离提供认证基础。

## 8. 半月文档撰写步骤

先确定本次半月范围和对应的两个工作周，再按以下顺序处理：

1. 浏览两个工作周内所有 commit 标题和涉及文件。
2. 按主题聚类，例如“图像生成”“历史会话”“子任务”“公司网关”“配置与部署”。
3. 为每个主题判断分类：新功能、bug 修复、功能改造、chore、官方分支合并。
4. 将连续提交合并成汇报语言。
5. 分别写两周的 `本周重点`，每周用 2 到 4 条概括核心功能模块和阶段成果。
6. 写分类条目，每类建议 1 到 5 条。
7. 两周详情写完后，在顶部生成 `汇总` 区域，复用两周 `本周重点` 中的模块主线。
8. 默认不输出 `参考提交`；只有用户明确要求面向开发人追溯时才增加。

### 8.1 本周重点写法

`本周重点` 用来说明这一周围绕哪些核心模块或能力主题完成了阶段性建设，不要复述“新增、修复、改造、chore”这些动作分类。

推荐格式：

```md
### 📌 本周重点
- Wiki 同步闭环：完成 Wiki 认证、凭证桥接、CLI 调用、线程元数据校验和自动同步能力建设。
- 视觉模型配置体系：完善默认视觉模型、OpenAI 协议、流式控制和配置版本升级。
- 跨平台运行稳定性：集中处理 Windows 沙箱路径、命令转义、网关日志和会话恢复问题。
```

写作要求：

- 每条以“功能模块 / 能力主题”开头，例如 `管理员用户管理`、`Wiki 同步闭环`、`视觉模型配置体系`。
- 冒号后写阶段成果或业务价值，不写 commit 细节。
- 不要把 `本周重点` 写成 `新功能`、`bug 修复`、`chore` 的摘要复述。
- 如果某周内容较少，可以只写 1 到 2 条，但仍应保持“模块：概括”的形式。
- 顶部汇总表中的 `核心模块` 列从这里提取模块名，`重点概括` 列用一句话合并本周主线。

## 9. 参考提交规则

`参考提交` 属于开发追溯信息，不是面向群同步或领导汇报的默认内容。

默认规则：

- 面向汇报、群同步、阶段复盘的文档不输出 `参考提交`。
- 面向开发人排查、代码审查、版本追溯的文档可以输出 `参考提交`。
- 如果用户没有明确要求保留 commit 信息，优先去掉。

需要输出时，建议：

- 每周保留关键 commit，不一定保留全部 commit。
- 如果当周提交数量很少，可以全部保留。
- 如果当周提交数量很多，优先保留每个主题的代表性 commit。

格式：

```md
### 参考提交
- `8f6e18e3` feat(config): 添加独立视觉模型配置支持
- `e824a333` feat(openai_image): 添加 OpenAI 图像生成 API 版本支持
```

## 10. 质量检查清单

生成最终 MD 前，需要检查：

- 是否覆盖了指定时间范围内的提交。
- 是否按两个工作周划分，且没有因周末或边界日期额外生成第三段。
- 是否所有日期均使用 `YYYYMMDD`，日期区间均使用 `YYYYMMDD-YYYYMMDD`。
- 是否按日期倒序排列，最近一周在最前面。
- 是否有顶部 `汇总` 区域，且通过序号对应到下方周详情。
- 汇总栏是否提炼了各周 `本周重点` 中的核心模块和重点概括，没有额外制造另一套表述。
- `本周重点` 是否使用“模块：概括”的形式，且没有复述新功能、bug 修复、chore 等动作类型。
- 是否只保留有内容的分类标题。
- 是否将连续提交合并成主题，而不是 commit 流水账。
- 是否区分了“主功能开发中的临时修复”和“独立 bug 修复”。
- 是否把文档、依赖、配置、性能、稳定性优化统一放入 `chore`。
- 是否保留了官方分支合并记录。
- 是否去掉了默认不面向汇报读者的 `参考提交`。
- 如果使用表情、图标或图表，是否已经先和用户确认样式。
- 是否适合直接复制给群里或领导阅读。
- 是否没有泄露敏感配置、密钥、内部账号等信息。

## 11. 推荐文件命名

半月汇总（默认）：

```text
开发记录汇总-YYYYMMDD-YYYYMMDD.md
```

单周汇总（仅用户明确要求时使用）：

```text
开发记录-YYYYMMDD-YYYYMMDD.md
```

半月汇总默认覆盖连续两个完整工作周，文件名使用两周首个工作日和最后一个工作日，例如：

```text
issue/_开发记录/202608/开发记录汇总-20260817-20260828.md
```

归档目录建议：

- 单月范围：放到对应月份目录，例如 `issue/_开发记录/202608/`。
- 跨月范围：优先按半月或月份拆成多个文档，分别放到对应月份目录，避免单个文档过长。
- 如果用户明确要求保留跨月总览，再额外生成跨月汇总文档。

示例：

```text
issue/_开发记录/202607/开发记录汇总-20260720-20260731.md
issue/_开发记录/202608/开发记录汇总-20260817-20260828.md
```
